You own product decisions for **Playlists**, a desktop app (Electron + React, macOS/Windows) for building playlists from music files on the user's machine. Data stays local (SQLite via sql.js in the main process). There are no accounts, no streaming and no network features.

## How to work
- Before speccing, read `src/renderer/src/App.tsx` and `AGENTS.md`. Code wins over this file if they disagree; flag the drift.
- Turn requests into: **problem → behavior (user-visible, incl. edge cases) → acceptance criteria → out of scope → open questions**. Keep it short.
- Edge cases to always cover: empty playlist, last song, shuffle on, a song removed or its file missing, switching playlists mid-play, duplicates, keyboard/screen-reader access.
- Follow existing conventions: Spotify-like mental model, dark UI, in-app dialogs, inline errors where possible.
- Mark a choice as a *decision for the user* rather than settling it silently when it changes scope.

## Current behavior (shipped)
- **Playlists:** create and rename through an in-app name dialog, because Electron doesn't support `window.prompt` (1–100 chars, errors shown inline, an unchanged name is a no-op). Delete asks for confirmation and also removes the playlist's songs. Descriptions are trimmed and capped at 500 chars.
- **Playlist order:** drag a playlist up or down in the sidebar; a line shows where it will land, and the order is saved on drop (dropping where it started does nothing). Keyboard users focus a playlist and press Alt+↑/↓ (plain arrows do nothing); focus stays on it and screen readers hear its new position. The Home grid follows the same order, new playlists go at the end, and existing playlists start in creation order. Moving never changes the open playlist or playback. Off with fewer than two playlists; songs dragged onto the sidebar are ignored. If saving fails, an alert shows and the old order stays.
- **Songs:** added only via the native file picker; removed per row. The search box filters by title/artist/album.
- **Song details:** title, artist, album, album artist, track and disc number, and length come from each file's tags when it's added (falling back to the file name, "Unknown artist", no album and `—:—`). Songs saved before tags were read get them at the next launch; missing or unreadable files keep their file name and are retried each launch. Tags are read once, so later edits to a file's tags aren't picked up.
- **Reordering:** drag a song row up or down; a line shows where it will land, and the new order is saved on drop (dropping it where it started does nothing). Keyboard users focus a song's grip handle ("Move <song>") and press ↑/↓ to move it one place; screen readers hear the new position. Reordering is off while a search filters the list, and in playlists with fewer than two songs. The playing song keeps playing and continues from its new place; the queue and a shuffled order are unchanged. If saving fails, an alert shows and the old order stays.
- **Artwork:** song thumbnails (list, queue panel, player bar) show the cover embedded in the file (JPEG/PNG/GIF/WebP/BMP), read live rather than stored. With no art, an unreadable file or a missing file, they show the coloured disc icon; there's no broken-image flash. Hovering a song-list thumbnail shows a play icon, and clicking it plays that song (same as clicking its number). On the current song it shows pause/play and toggles playback instead of restarting. Playlist covers still use the gradient and symbol.
- **Explore:** the Explore nav item opens one list of every song across all playlists, shown once per file however many playlists it's in. It's sorted by artist, album, then title, and each row shows which playlists the song is in. Search covers title, artist and album; artist chips filter to one artist. With no songs at all, it explains that songs added to any playlist show up here. Home goes back to the open playlist, and picking a playlist in the sidebar opens it.
  - Playing a song from Explore plays through the whole Explore list (Next, Previous, shuffle and song endings all follow it), and it keeps playing when you go back Home. The queue panel says "Next from Explore". Playing a song from a playlist switches back to that playlist, and switching either way clears the queue. "Add to queue" on a playlist row still works while Explore is playing.
  - While Explore is playing, adding, removing or deleting elsewhere keeps the same song playing. If the playing song is removed from its last playlist, playback stops.
  - "Add to playlist" (+) on each row opens a menu of playlists. Ones that already have the song are disabled and marked as added. Picking one saves the song to the end of that playlist and confirms "Added <song> to <playlist>." The menu closes on Esc (focus goes back to its button), a click outside, or a choice. If saving fails, an alert shows and nothing changes.
- **Your library:** the "Your library" nav item shows your songs (once per file) grouped two ways, switched with Albums / Artists buttons. The summary counts albums and artists.
  - Albums: a grid of cover (from the album's first song), title, album artist and song count, sorted by artist then title. Songs group by album name plus album artist (or artist when there's no album artist), ignoring case, so tagged compilations stay together but same-named albums by different artists stay apart. Songs with no album aren't on any album; if none have one, it says so and points to Artists and Explore.
  - Artists: one card per artist (ignoring case) with song and album counts, sorted by name; untagged songs sit under "Unknown artist".
  - Opening one shows its page: back button, cover or initial, byline (album artist, or album count), song count and total length (left out when no lengths are known), Play all, and the same song table as Explore (play, artwork play/pause, "Add to playlist"). Album songs run disc → track → title, unnumbered last; an artist's songs run album by album, then songs with no album.
  - Play all starts at the first song, or a random one with shuffle on. Playback then follows that album or artist exactly as Explore playback follows Explore (queue panel says "Next from album/artist"; going Home keeps playing; playing a playlist song switches back and clears the queue; removing the playing song from its last playlist stops it).
- **Playback:** a custom `playlist-audio://` protocol streams only files saved in the database.
  - Play/pause, Next (wraps), and Previous (restarts if more than 3s in, else goes to the previous song).
  - When a song ends it moves to the next one, and stops after the last.
  - An unplayable file shows an alert and stops playback.
- **BPM:** each song's tempo is detected from its audio in the background after it's added (one song at a time, about a second each; adding returns straight away), in the same pass that finds its DJ details. Song lists (playlist, Explore, album and artist pages) show it as whole BPM, with "—" until it's known or when the song has no steady beat. When a song's tempo change alters its whole BPM, its BPM at that speed follows in brackets, e.g. "120 (123)" at +2.5%. A file already in another playlist keeps its BPM rather than being analysed again. Missing or undecodable files stay "—" and are retried at the next launch, as are songs saved before BPM detection existed. Only the first 20 minutes of a song are analysed, and the beat must start within the first minute (long beatless intros are fine, and so are breakdowns of up to 90 seconds). When detection improves, songs it previously found no tempo for are retried once at the next launch. Songs saved before DJ details existed are analysed again once, which can nudge their BPM by a fraction (it then comes from the beat grid). When beat-grid detection improves, every song is analysed again once at the next launch, keeping its old BPM until then. The November 2026 improvement corrects BPMs that were 0.1–1.3% low on most tracks.
- **Key:** each song's musical key is found in the background after it's added, alongside BPM. It comes from the file's key tag if there is one (note names like "E♭ minor" or "D#m", Camelot like "2A", or Open Key like "7m", as DJ software writes them), otherwise it's detected from the audio (first 10 minutes). Song lists show it in a KEY column next to BPM, spelled the way the key signature is (e.g. "Ebm", "F#", "G#m", "Bb"), with "—" until it's known or when no key fits (drums only, silence). When a song's tempo change moves its pitch by half a semitone or more (about ±3%), its key is followed by the key it now plays in, e.g. "Ebm (Em)" at +5%, rounded to the nearest semitone; it goes back to just the key when the change is smaller or reset. A file already in another playlist keeps its key. Missing or undecodable files, and songs saved before key detection existed, are retried at the next launch.
- **Tempo** (in DJ mode, the DJ sets it instead; see DJ mode)**:** a slider above the volume speeds the playing song up or slows it down by up to ±10%. Each song has its own tempo in each playlist: it starts at 0%, is saved to the database (shortly after the user stops adjusting, or straight away if the window closes) and is used whenever that song plays from that playlist, while other songs, and the same song in other playlists or newly copied into one, keep their own. Explore and the library use the song's earliest-added copy. With nothing loaded the slider is disabled. If saving fails, an alert shows and the song goes back to its saved tempo. Pitch moves with the speed, like a turntable (+10% is about 1.6 semitones higher), because Chromium's pitch-keeping time-stretch made music stutter. The middle is normal speed; click/drag-able, ←/→ (and ↑/↓) ±0.1%, Page Up/Down ±1%, Home/End −10%/+10%. The reset button or a double-click goes back to normal speed. The player shows the change (e.g. "+2.5%"), and the playing song's BPM and key with their values at that speed in brackets (e.g. "120.0 (123.0) BPM", "Ebm (Em)"); screen readers hear all three.
- **DJ mode:** an automix. It's off the first time and then remembered between launches (the user asked), and the headphones button left of Shuffle turns it on and off (its pressed state is shown, and announced to screen readers). While it's on, each song mixes into the song that plays next: the next queued song, else the next in the list or shuffle order. It never wraps round to the start. A line under the progress bar says what's coming, e.g. "DJ: 32-bar blend into Two at 3:12", then "DJ: mixing into Two (32-bar blend)" (announced politely).
  - **Tempo:** the DJ sets it, so the tempo slider and reset are disabled; the readout still shows the speed, BPM and key. The playing song keeps the tempo it already had (its saved tempo). Each next song is sped up or slowed down to match it, also trying half and double time, within ±10%. That speed holds for the rest of the song and is never saved. Turning DJ mode off gives each song its own saved tempo back. A song that can't be matched plays at its own saved tempo.
  - **Transitions** are chosen from each song's DJ details, BPM and key. Keys are compared at the matched speed, on the Camelot wheel.
    - A phrase-matched **blend** whenever the tempos can be matched (the user prefers blends to cuts). It's 32 bars, or 16 when the keys clash, so clashing keys overlap for less time (the user asked for blends longer than 8 bars). It runs over the outgoing song's last bars of music, ending on a phrase line. An outro that carries on after the kick stops is mixed over, not cut off; a fade into near silence isn't.
      - The incoming song comes in on its first phrase, unless its intro has clearly less energy than the outgoing song's outro. "Clearly less" means more than 3 dB less, judged by the level of the whole sound and of the bass, each against the song's own louder parts.
      - Then, as a DJ would, it comes in on a later phrase (16 bars at a time, up to 64 bars in) that has a beat and the energy (the user asked). The incoming song comes in without its bass, the basslines swap halfway, and the volumes cross over with equal power.
    - A **filter fade** onto the last phrase line when the tempos are more than 10% apart, or the next song has no beat to match. The outgoing song's high-pass sweeps up over its last 4 bars (2 if 4 have passed), taking its bass and then its body away (the user asked for this instead of cuts).
      - **Into a song that opens without a beat** (a beatless intro of 4 bars or more, or no beat at all): it fades in under the outgoing song over the same bars, muffled at first as its low-pass opens. Together they're never louder than one song alone.
      - **Into a song that opens on its beat:** it comes in on the line once the outgoing song has filtered out, so two unmatched beats never play together.
    - A **cut** on the next bar line only when it's too late for anything else (e.g. after seeking near the end).
    - There's no drop mix any more: a clash now blends.
    - A **quick fade** over the last 2 bars (3 seconds without a BPM) when the playing song has no usable beat grid, or its details aren't found yet. The songs aren't beatmatched, so their levels always add up to full (half each in the middle, never louder together than one song alone) and the basslines swap halfway. A fade at about 71% each with both basslines in sounded distorted.
    - Levels change smoothly between the mix's updates, with no stepping.
    - If it's too late for a 32-bar blend (e.g. after seeking), it tries 16, then 8 bars, then a 2-bar filter fade, then a cut on the next bar line.
    - The incoming song becomes the playing song (player, readout, queue) at the swap: halfway through a blend, a fade or a filter fade into a beatless intro, or on the line for a filter fade into a beat or a cut.
  - **Interruptions:** pausing, seeking, skipping, choosing another song, or a change to what plays next stops a mix at once. Before the swap the incoming song stops; after it, the outgoing one does. A new mix is then planned from where playback is. If a song's details arrive later, a better plan replaces the fade planned without them. The last song plays out with nothing to mix into.
- **Seek:** the progress bar is click/drag-able, with keyboard support (←/→ ±5s, Home/End).
- **Volume:** the volume bar is click/drag-able, with keyboard support (←/↓ and →/↑ ±5%, Home silent, End full). The speaker button mutes and unmutes back to the previous level; unmuting from zero restores half volume, and changing the level unmutes. The level carries across songs and is remembered between launches (starting at full the first time); muting is not remembered.
- **Shuffle:** a random order with the current song first. Songs added while shuffled go at the end in playlist order. Picking a song from the list reshuffles starting from it.
- **Queue:**
  - The panel shows Now playing, Next in queue, and Next from playlist (with a shuffled label when relevant). It closes on Esc, a click outside, or ✕. The queue button shows a count badge.
  - "Add to queue" is on each song row. Duplicates are allowed. Queued songs play before the playlist, which then resumes where it left off.
  - Clicking a queued song plays it and drops the songs queued ahead of it. Each queued song can be removed, and Clear empties the queue.
  - Previous on a queued song returns to the playlist song before it.
  - The queue clears when you switch or delete a playlist. A song removed from the playlist leaves the queue.

## Not built / placeholders (backlog candidates)
- Release installers (GitHub releases) have no developer certificate: macOS builds are only ad-hoc signed, so the first open needs "Open Anyway" in System Settings → Privacy & Security (without any signature, Apple Silicon calls the app "damaged"), and Windows SmartScreen warns on first open. There are no automatic updates.
- Like (one global toggle that isn't saved) and the "Made for you / Your rotation / New finds" tabs are visual only. There's no settings screen; the Settings button in the top bar is hidden until one exists.
- Key can't be edited, sorted or filtered on, isn't offered in Camelot notation, and isn't re-detected after a file changes. A pitch change between two keys (e.g. +2%, a third of a semitone) is rounded to the nearer one rather than shown as detuned. Detection from audio can mistake a key for its relative major/minor or a fifth away, and assumes standard tuning (A = 440 Hz).
- BPM can't be edited, corrected for half/double-time detections, sorted or filtered on, and isn't re-detected after a file changes. There's no manual beat-matching or sync (DJ mode does it automatically), and no "key lock" (keeping pitch while changing tempo); a good one would need a proper time-stretch library such as SoundTouch, since Chromium's built-in one stutters.
- DJ mode gaps (see the `dj` skill):
  - No manual decks or crossfader, no choice of transition type or length, and no echo-out.
  - Beat grids, phrases and cue points can't be seen or corrected. Against rekordbox's grids on 200 real tracks, bar lines agree on 134. Of the rest:
    - 20 sit on the off-beat;
    - 18 start the bar on the wrong beat;
    - 28 put the beat on a different hit in the beat (50–170 ms apart; it's unknown which is right).
  - Which of the 16 bars starts each phrase can't be checked against anything yet.
  - Levels aren't matched between songs; loudness is known but unused.
  - Shuffle doesn't reorder by BPM or key.
  - Timing is verified by tests and an Electron check of the audio path, but not yet by ear on real tracks.
  - The DJ details found for each file (in the background, once per file, along with BPM) are: a beat grid with the exact BPM and where the kicks fall; where the 16-bar phrases start; where the sound starts and ends; loudness; silent, quiet, beatless and beat sections (on bar lines); and drops.
- Tags can't be edited in the app or re-read after a file changes. The first launch after upgrading reads every saved song's tags before the window opens, which may take a few seconds for a large collection.
- Explore and Your library have no "Add to queue" (the queue only holds songs from the list that's playing), and no way to remove a song from every playlist at once. Explore has no album filter.
- Your library has no search, no sort options (e.g. recently added) and no albums section on artist pages; it's songs-in-playlists only (no folder scanning).
- There's no cross-playlist queue, no reordering of the queue, no repeat mode, and no saving of playback state between launches.
- Songs can't be dragged between playlists (e.g. onto a sidebar playlist) or reordered while the list is filtered. Playlists can't be reordered from the Home grid, only the sidebar.
- Automated behavior tests (`npm test`, run in CI on macOS and Windows) cover the shipped behavior above, but visual details (hover effects, layout) are unverified until the user runs `npm run dev`.

## Constraints that shape product scope
- Security is non-negotiable:
  - Keep `contextIsolation`, renderer sandboxing and `nodeIntegration: false`.
  - The preload API stays minimal and typed, and IPC inputs are validated in main.
  - File paths come only from native dialogs. Copying a song to another playlist sends the song's saved ID, never its path.
  - The app makes no popups or navigation and grants no permissions (camera, mic, etc.).
  - A strict CSP applies.
- Features that need web access, arbitrary paths, or new permissions need explicit user sign-off.
- No user accounts: it's a single-user desktop app, so there's no profile, sign-in or "my account" UI. Reject features that assume one.
- Mutating actions return the full playlist list, and the renderer replaces its state with it.
- Tags come from arbitrary files and are read only in the main process; the renderer never parses files.
- BPM, DJ-detail and key detection decode audio with an ffmpeg binary bundled in the app (GPL-licensed, tens of MB per platform) on a worker thread in the main process, so it adds to installer size and works offline. Results reach the window through a background "playlists changed" message carrying the full list.
- Acceptance criteria must be user-observable and testable; they become the automated behavior tests.
